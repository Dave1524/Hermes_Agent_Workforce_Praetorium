**Status:** Not started

## Objective

Two tightly related improvements to the agent tasking system:

1. **NUC-34** — Add structured priority/deadline fields to `queue.md` so agents can prioritise correctly, and make the EOD-wrap process reliably regenerate it.
2. **NUC-32** — Give the M1 weekly market-signal scan its own dedicated systemd timer so it runs every Monday at 05:30 regardless of the generic agent-proposal queue lottery.

---

## Why / Problem

### NUC-34

The agent task queue (`04_operations/box_brief/queue.md` in the vault) is a flat markdown list. The only priority signal is "top OPEN item." There is no deadline field. In practice:

- An ad-hoc July 09 insert buried a deadline-bound task (`Q-2026-07-08-1`, due 07-14) that was later closed unexecuted.
- Agents pick tasks semi-randomly from the open list — a task with a near-term deadline has no structural way to signal urgency.
- The EOD wrap (which should regenerate `queue.md` nightly) has not run a full regeneration since July 09.

### NUC-32

The M1 weekly signal scan has a dedicated task profile (`profiles/m1_signal_scan_task.md`) but no dedicated systemd timer. It runs through the generic `agent-proposal.timer` which selects agents by queue lottery. This means:

- M1 competes for a slot with all other agent profiles (BD stall radar, weekly pre-assembly, etc.).
- It can be delayed or skipped if other tasks fill the queue.
- The profile itself has a manual "max 1×/week" guard, but a dedicated timer would make the cadence reliable by design.

## Implementation Plan

### Part A — NUC-34: Queue Semantics

#### Step A1 — Define the queue.md schema

Update the queue.md template in the vault to use a structured table for each open task. The table columns should be:

```
| Priority | Task ID | Deadline   | Description                              | Status |
|----------|---------|------------|------------------------------------------|--------|
| P1       | Q-...   | 2026-07-21 | DP World — follow-up proposal            | OPEN   |
| P2       | Q-...   | 2026-07-28 | Rhenus — cold chain automation brief     | OPEN   |
| P3       | Q-...   | (none)     | Boltrics — coffee follow-up              | OPEN   |
```

Rules:
- **Priority:** P1 (must complete this week), P2 (this sprint), P3 (when bandwidth permits)
- **Deadline:** ISO date or blank
- **Status:** OPEN / IN PROGRESS / DONE / CANCELLED
- **New rows are appended below OPEN rows only** — this preserves the "top OPEN item" semantics but gives agents a richer signal

#### Step A2 — Update task profiles to read the new schema

Update the priority-selection logic in agent task profiles that read `queue.md`:

**`profiles/claudius_task.md`** (and others):
```
Old: "the OPEN queue.md item with the soonest Deadline"
New: "the OPEN queue.md item with the highest Priority × closest Deadline"
```

Specifically:
1. Read `queue.md` from the vault via `qmd get 04_operations/box_brief/queue.md`
2. Parse the table, filter to `Status = OPEN`
3. Sort by `Priority` (P1 > P2 > P3) then by `Deadline` (soonest first)
4. Pick the top item

#### Step A3 — Fix EOD-wrap regeneration

The EOD wrap process should regenerate `queue.md` each night. This is a vault-level document update. The mechanism is:

- Add a step to the nightly `agent-proposal.timer` (or a companion script) that calls a deterministic script to regenerate `queue.md` from the active Notion task state (or the Task Inbox database).
- **Or:** Make the EOD wrap agent (claudius's eod-wrap skill) include `queue.md` regeneration in its task list, with the new structure.

Preferred approach: **deterministic script** (no LLM). A small shell/Python script that:
1. Reads the current state from the vault's queue.md (preserving DONE items as a log)
2. Cross-references against the Task Inbox Notion database for new tasks
3. Rewrites the OPEN section with fresh Priority/Deadline assignments
4. Writes the updated file to the inbox worktree for Mac-side review

#### Step A4 — Document the convention

Add a brief document at `docs/queue_convention.md` describing:
- The queue.md table schema
- How Priority and Deadline are assigned
- How agents should read and interpret the queue

### Part B — NUC-32: M1 Timer

#### Step B1 — Create the M1 override env file

Following the `bd_stall_radar.env` pattern:

**`~/.config/agent-workforce/m1-signal-scan.env`:**
```
# M1 — Market Signal Scan override env.
# Wired to agent_propose.sh via AGENT_JOB_OVERRIDES (see systemd/m1-signal-scan.service).
# Injected as a heredoc before the standing task — keeps the task profile clean
# and makes the timer/env pair the unit of deployment.
AGENT_NAME=Claudius
AGENT_PROFILE=claudius
AGENT_TASK_FILE=/home/dave/agent-workforce/profiles/m1_signal_scan_task.md
```

#### Step B2 — Create the systemd service unit

**`systemd/m1-signal-scan.service`:**
```ini
[Unit]
Description=M1 weekly market signal scan — NUC-32
After=network-online.target qmd-mcp.service brave-mcp.service
Wants=network-online.target brave-mcp.service
ConditionPathExists=/home/dave/agent-worktrees/inbox

[Service]
Type=oneshot
User=dave
Environment=AGENT_JOB_OVERRIDES=/home/dave/.config/agent-workforce/m1-signal-scan.env
EnvironmentFile=/home/dave/.config/agent-workforce/secrets.env
ExecStart=/home/dave/agent-workforce/bin/agent_propose.sh
TimeoutStartSec=45min
NoNewPrivileges=true
```

#### Step B3 — Create the systemd timer unit

**`systemd/m1-signal-scan.timer`:**
```ini
[Unit]
Description=Schedule M1 weekly signal scan — Mon 05:30 Europe/Amsterdam — NUC-32

[Timer]
OnCalendar=Mon 05:30
RandomizedDelaySec=3min
Persistent=true

[Install]
WantedBy=timers.target
```

#### Step B4 — Deploy via deploy-staging

Copy units to `/etc/systemd/system/`, enable and start the timer:

```bash
sudo cp systemd/m1-signal-scan.service /etc/systemd/system/
sudo cp systemd/m1-signal-scan.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now m1-signal-scan.timer
```

#### Step B5 — Register in status script

Add `m1-signal-scan.timer` to the list in `bin/praetorium-status.sh` (line ~11) so it appears in the daily status output.

## Risk & Open Questions

- **queue.md is vault-located** — changes to queue.md must go through the inbox workflow (propose → Mac-approve → sync), not edited directly by the box. The regeneration script should write to the inbox worktree as a proposal, not mutate the vault directly.
- **M1 env file location** — `~/.config/agent-workforce/` vs. `agent-workforce/config/`? Existing pattern is `~/.config/agent-workforce/` (see bd_stall_radar.env). Stick with that — secrets and config stay outside the repo.
- **EOD wrap fix** — This is the harder part. The current EOD wrap is an agent task (claudius's eod-wrap skill). Making it reliably regenerate queue.md means either (a) adding it as a deterministic step in the nightly pipeline, or (b) making the EOD agent's task instructions explicit about it. Option (a) is more reliable.
- **M1 timer vs. profile self-guard** — The M1 profile already has a "max 1×/week" guard. The timer makes it fire weekly; the profile guard prevents double-fires if manually triggered. They complement each other.
